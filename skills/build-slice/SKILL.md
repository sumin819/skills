# 입력에서 결과까지 하나를 완성하기

기존 실행 명령과 관련 코드부터 읽는다. 변경 전에 핵심 흐름이 현재 실행되는지 확인하고 기존 실패를 구분한다. 문제에 맞는 구현 스택이 이미 있다면 유지한다.

첫 단위는 입력 → 처리 → 출력이 이어져야 한다. 웹 기능이면 실제 사용자 행동 하나, 분석이면 데이터 로드에서 결과 파일까지, API면 요청에서 응답까지를 완성한다. UI만 먼저 만든 뒤 실제 계산을 나중에 채우는 방식은 피한다.

구현 전 성공 사례 하나와 중요한 실패·경계 사례를 고른다. 위험에 맞는 검증을 추가한다. 단순 문구 수정에 불필요한 테스트를 늘리지 않는다. 규칙 계산·집계·판정은 재현 가능한 코드로 처리하고 LLM 호출은 필요성과 허용 여부가 확인된 경우에만 사용한다.

오류가 나면 다음 순서로 좁힌다.

1. 실행 명령, 입력, 실제 오류를 확보한다.
2. 가장 작은 재현 사례를 만든다.
3. 증거와 맞는 가설 하나를 선택해 최소 수정한다.
4. 원래 실패 입력과 인접한 정상 입력을 다시 확인한다.

같은 실패가 반복되면 무작정 패키지를 바꾸지 말고 가설과 환경을 다시 확인한다. 시간 대비 가치가 낮은 기능은 범위 축소를 제안한다. 실행하지 않은 경로는 미검증으로 남긴다.

실제 실행법, 중요한 설계 선택과 이유, 검증 결과를 과제 지정 문서 또는 `PRD.md`에 기록한다. 브라우저를 직접 확인할 수 없다면 서버 응답 검증과 화면 확인 여부를 분리해서 보고한다.
